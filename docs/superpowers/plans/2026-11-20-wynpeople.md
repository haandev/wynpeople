# WynPeople Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the WynPeople CoreHR + PTO system as a zero-backend app: the whole data model, business logic, and security on the Wyndbase base `wynpeople`, plus a React client modelled on BambooHR's information architecture.

**Architecture:**
- **Base:** All logic lives in the base, in this order of preference: constraints, then DCL rules, then elevated named queries, then flows (interaction, schedule, table triggers). The base model is applied through Wyndbase MCP tools. Every definition is also kept as source under `base/`, so it can be reviewed and re-applied.
- **Client:** Vite + React. It talks to the base only through `@wyndbase/sdk`, with types generated by `wyndbase typegen`.

**Tech Stack:**
- Wyndbase 0.1.3-preview (WQL, DCL, flows)
- Bun, Vite 5, React 18, TypeScript 5, TanStack Router + Query v5, Tailwind 3
- SheetJS (`xlsx`), `jspdf` + `jspdf-autotable`, Vitest

**Spec:** `docs/superpowers/specs/2026-11-20-wynpeople-design.md`. Its "Rev 2" section takes precedence over §5.

## Global Constraints

- Server `https://dev.wyndbase.dev`. Base `wynpeople`. Never read, list-into or query base `wynhr`, and never touch the memory directory.
- Zero backend: no server code of our own. The client calls only SDK typed trees (`wyndbase.query.*`, `wyndbase.mutation.*`, `wyndbase.wql('literal')`). No `fetch` to product routes, and no hand-written row types.
- Client-callable named queries use `DEFINE OR REPLACE public …`. Elevated ones add `GRANT call ON <space>.<name> TO <roles>`. Anonymous access stays off.
- Every Wyndbase misbehaviour or hard-to-find feature goes into `wyndbase-findings.md` immediately, using the template in that file. Record the first attempt, and update the summary counts.
- After a named write (`$x := INSERT … -> {…}`), never read the same table in the same submission. Return what you need from `->`, or use a bare write. (Findings: bug.)
- Never use one-to-one links. Use many-to-one + `unique` instead. (Findings: bug.)
- Before dropping a table or space, drop the links pointing into it from other spaces. (Findings: bug.)
- Never write an effective column's value from the same row's effective column. SELECT it first and bind it.
- Test users: `you+<username>@example.com`. Never enter or ask for passwords; accounts get a set-password mail.
- SMTP: `HOST=192.168.1.31`, `PORT=25`, `SECURE=false`, `FROM_EMAIL=wyndb@developertools.com`. `config.host` is the env key name `SMTP_HOST`.
- Decimal hours: `decimal` with precision 10 and scale 4 everywhere in `pto`.
- UI copy is in English. The layout is inspired by BambooHR, but uses no BambooHR name, logo, colours or copy.

## Review Focus

1. **Correction vs change misuse.** A correction issued on a period whose start ≠ the period start must change nothing and say so. Test: Task 3 `correct_requires_period_start`.
2. **Manager reassignment with a pending request.** The pending interaction must move to the new approver, and the old approver must get 403. Test: Task 8 `reassign_moves_pending_request`.
3. **Report leakage through raw WQL.** An employee running `SELECT hr.compensation {*}` or `SELECT hr.employees { terminationReason }` must get no rows or nulls. Test: Task 4 `raw_wql_cannot_read_salary`.
4. **Partial day below 2 h and requests spanning a holiday or weekend.** The first is refused; the second counts only working hours. Test: Task 7 `partial_day_minimum` and `holiday_not_counted`.
5. **Accrual run twice for the same pay period.** The second run writes nothing (idempotent key). Test: Task 9 `accrual_idempotent`.

## File Structure

```
base/                       source of truth for what is applied through MCP
  schema/<space>.<table>.json   design_table payloads (columns, constraints, metadata)
  rules/<area>.wql              DCL statements (GRANT/PREVENT/POLICY)
  queries/<space>.<name>.wql    DEFINE OR REPLACE statements, one per file
  flows/<space>.<name>.json     create_flow payloads
  seed/*.wql                    seed statements
  tests/<area>.md               verification queries with expected results (run via run_wql / targetUserId)
app/                        Vite React client
  src/wyndbase.ts               SDK client + session
  src/routes/…                  TanStack file routes (one folder per top tab)
  src/features/<area>/…         components + hooks per area
  src/lib/export/{csv,xlsx,pdf}.ts   export writers sharing one metadata header
  wynpeople.wql.gen.d.ts        generated types (never edited)
wyndbase-findings.md
```

### Task 7: PTO core queries — calendars, balances, requests

**Files:**
- Create: `base/queries/pto.*.wql`, `base/rules/pto.wql`, `base/seed/pto.wql`, `base/tests/pto.md`

**Interfaces:**
- Produces (all public; elevated only where noted):
  - `pto.generatePayPeriods { country, frequency, year }` (elevated, hr_admin). `monthly` produces 12 periods, `semi_monthly` 24 (1–15, 16–end), and `biweekly` produces 14-day periods starting at the first Monday of the year.
  - `pto.copyHolidays { country, fromYear, toYear }` → draft rows; `pto.activateHolidays { country, year }` (elevated, hr_admin and hr_manager).
  - `pto.leaveYear { country, onDate } -> { start, end }` (public; from `org.country_settings`).
  - `pto.policyFor { employeeId, typeId, onDate } -> policy row`: the override wins, otherwise match on (country of `office` unit, `employmentType`).
  - `pto.workingHours { employeeId, startDate, endDate, partial?: [{date, hours}] } -> { days: [{date, hours}], totalHours }`. Excludes the country's `weekendDays` and active holidays; full days use the policy's `hoursPerDay`.
  - `pto.balances { employeeId?, asOf? } -> rows { typeId, typeName, unlimited, accrued, used, pending, remaining, projectedAtYearEnd }`. With no `employeeId` it uses self. Rows are scoped by the ledger read rules.
  - `pto.submitRequest { typeId, startDate, endDate, partial?, note? } -> { requestId }` (policied, self only). ASSERTs, in order:
    1. No overlap with the caller's pending or approved requests.
    2. Each partial day ≥ `minPartialHours`.
    3. `totalHours > 0`.
    4. Unless `unlimited`: projected balance at `startDate` − `totalHours` ≥ −`negativeBalanceLimitHours`.
  - `pto.cancelRequest { requestId, reason? }`:
    - Self may cancel pending at any time, and approved only while `startDate > current_date`.
    - HR may cancel anything.
    - On approved, writes `reversal` ledger rows.
  - `pto.adjustBalance { employeeId, typeId, hours, reason }` (elevated; hr_admin, and hr_manager for their office).
  - `pto.whoIsOut { from, to, departmentTeamId?, officeTeamId? }`: name, type category and dates only. The type name is hidden from non-HR, non-manager callers.
  - `pto.myRequests { employeeId? } -> rows { requestId, type, startDate, endDate, totalHours, status, decidedBy, decidedAt }` (defaults to self; policied).
  - `pto.saveType { typeId?, code, name, category, paid, color, active }` (elevated, hr_admin).
  - `pto.changePolicy { policyId?, effectiveFrom, type, country, employmentType, accrualMode, …all policy fields } -> { policyId, pendingRecalcId? }` (elevated, hr_admin). When `effectiveFrom < current_date` it inserts `pto.pending_recalcs`.
- Rules: the ledger and requests read scope mirrors `hr.employees` (self / manager / HR office / HR admin), and writes happen only through the named queries.

### Task 9: Accruals, annual grants, year end, status-change effects

**Files:**
- Create: `base/queries/pto.runAccruals.wql`, `base/queries/pto.runYearEnd.wql`, `base/queries/pto.onStatusChange.wql`, `base/flows/pto.accrualRun.json`, `base/flows/pto.yearEnd.json`, `base/flows/hr.syncApprovers.json`, `base/tests/accrual.md`

**Interfaces:**
- Produces:
  - `pto.runAccruals { asOf: date }` (elevated; GRANT call hr_admin; flows run as the service).
    - **per_period:** for every pay period with `periodEnd = asOf`, every employee whose policy is `per_period`, whose frequency matches, and whose status on `periodEnd` is active (or leave with `accrueDuringLeave`):
      - `hours = round(accrualHoursPerPeriod × f, 4)`.
      - `f = activeDaysInPeriod / periodDays` when `prorateFirstPeriod` and hire/termination falls inside the period, else 1.
      - Capped so that this leave year's accruals ≤ `accrualCapPerYear`.
      - Writes `INSERT pto.ledger EACH (SELECT …)` with `idemKey = 'acc:'||employee||':'||type||':'||payPeriod` (no batch).
    - **annual_grant:** on the country's leave-year start, writes the grant; for a hire later in the year, prorates by remaining months / 12. `idemKey = 'grant:'||employee||':'||type||':'||leaveYearStart`.
    - Writes one `pto.accrual_runs` row.
  - `pto.runYearEnd { asOf }`:
    - For each country whose leave year ends on `asOf`:
      - `carryover = min(remaining, maxCarryover)` as `carryover` rows dated the next day.
      - The excess goes to `expiry`.
      - Carried hours older than `carryoverExpiresAfterMonths` expire.
    - Idempotent by `idemKey`.
  - `pto.onStatusChange { employeeId, effectiveFrom, newStatus }`: on `terminated`, cancels future pending/approved requests and writes `payout` or `forfeit` for the remaining per-policy balance.
  - Flows:
    - `pto.accrualRun` (schedule `15 0 * * *`): wql `pto.runAccruals { asOf: today }`, then `pto.runYearEnd`.
    - `hr.syncApprovers` (schedule `5 0 * * *`): select employees whose stored `approver` ≠ the computed approver, or whose team memberships ≠ the effective department/productTeam/office today; repeater → wql update / `moveTeamMember`.

  - `accrual_idempotent`: running 2026-11-30 again → 0 new rows.
